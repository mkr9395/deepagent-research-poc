  1. Recommended architecture

  One orchestrator Deep Agent and one reusable researcher subagent definition.
  The orchestrator is spawned once per run. The researcher is spawned several
  times, once per task.

  User request
     │
     ▼
  Orchestrator (create_deep_agent)
     ├─ write_todos            → plans the research
     ├─ write_file             → writes research_plan.md
     ├─ task(researcher) ×N    → delegates, one per company+topic
     │      └─ tavily_search (capped) → writes findings to notes/*.md
     ├─ read_file / ls         → reads the notes for synthesis
     └─ write_file             → report.md (final)

  The orchestrator parses the companies and dimensions out of the request. It
  does not need a separate classifier step. For the JPMorgan/BofA example it
  should add banking-specific angles such as net interest income and regulatory
  capital. This is a prompt-level instruction, not code.

  2. Where Deep Agents is used

  - Planning: the built-in write_todos tool, which the system prompt tells the
    agent to use first. The todo list is the research plan.
  - Subagents: the built-in task tool, configured through
    create_deep_agent(subagents=[...]).
  - Filesystem: the built-in ls, read_file, write_file and edit_file tools. A
    FilesystemBackend points them at a local workspace/ folder.
  - Our code: about 100 lines. It covers a Tavily tool wrapper, the researcher
    spec, the system prompt and a CLI entry point.

  We write no graph and no routing logic. The agent's behavior comes from the
  prompts and the tools it is given.

  3. Where delegation happens

  The orchestrator calls task("researcher", ...) once per company+topic. A
  typical run has 2 companies × 2–3 topic groups, so 4–6 calls. Example topic
  groups:

  - Revenue and profitability
  - Risks
  - Outlook

  The researcher gets a narrow brief, such as "Microsoft: last 4 quarters
  revenue growth and margins". It searches, writes a detailed notes file with
  source URLs, and returns only a 3–5 line summary plus the file path. That
  keeps the orchestrator's context small.

  4. Filesystem context management

  workspace/
    research_plan.md
    notes/microsoft_financials.md   ← full detail and URLs, written by the
  subagent
    notes/alphabet_risks.md
    report.md                       ← final comparison

  - Detailed research lives on disk. The orchestrator context holds only short
    summaries and paths.
  - During synthesis the orchestrator reads the notes files it needs.
  - I'd use FilesystemBackend(root_dir="workspace", virtual_mode=True) so the
    agent can't write outside that folder.
  - The final report is saved by the agent itself with write_file. That is the
    "save as markdown" requirement. It is also easy to inspect afterwards, which
    is useful for a POC demo.

  5. Limiting Tavily usage

  Several layers, all cheap to build:

  1. A custom tool wrapper, not the raw Tavily tool. It enforces a hard per-run
     budget (for example 12 searches). Once the budget is spent it returns
     "budget exhausted, write up what you have". The agent can't loop past it.
  2. A per-subagent guideline in the prompt: at most 2–3 searches per task, with
     specific queries.
  3. Cheap search settings: search_depth="basic", max_results=3-5, and no raw
     page content.
  4. An in-memory cache keyed on the query, so duplicate queries cost nothing.
  5. Logged counts. The wrapper prints the query and the running count, which
     also makes the demo easy to follow.

  1. Install deepagents, langchain-tavily (or tavily-python) and python-dotenv.

  2. Build a minimal agent with no subagent, and run one query to confirm the

  Why: Researcher work is narrow: search, extract numbers, write notes. A

    model can probably do it, but I'd test that rather than assume it.

  Why not go smaller on the orchestrator: Deep Agents injects a long system
  prompt covering the todo, filesystem and task tools. Nano-class models are
  more likely to skip write_todos, pass vague briefs to the subagent, or answer
  directly. That would hide the Deep Agents behavior you want to demonstrate.

  Why not gpt-5-mini or other reasoning models: they are more capable but
  slower, and their reasoning tokens add cost. That is more than this POC needs.
  If gpt-4.1-mini struggles, it is the first upgrade to try.

  Configuration

  Both models would be set through environment variables:

  OPENAI_API_KEY=...
  TAVILY_API_KEY=...
  ORCHESTRATOR_MODEL=gpt-4.1-mini
  RESEARCHER_MODEL=gpt-4.1-mini

  Swapping models later is then a .env edit, with no code change. Deep Agents
  accepts model strings like openai:gpt-4.1-mini, so the langchain-openai
  package is the only extra dependency.

  - Smaller models will write thinner, less nuanced comparisons. For a POC the
    goal is to show the plan, the delegation, the files on disk and a coherent
