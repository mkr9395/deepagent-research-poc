> which parts are provided by Deep Agents?

● Provided by Deep Agents (the deepagents package):
  - create_deep_agent: the agent loop itself. We don't write one.
  - write_todos: the planning tool the orchestrator uses for its research plan.
  - task: delegation to a subagent. It runs the researcher in "isolated" mode,
    so it sees only the brief, and the parent gets back only its final message.
  - Filesystem tools: ls, read_file, write_file, edit_file, glob and grep, plus
    FilesystemBackend, which we sandbox to outputs/research/ with
    virtual_mode=True.
  - Subagent and middleware plumbing: the SubAgent spec format and the way
    middleware wraps tool calls.

  Ours, plugged into Deep Agents:
  - Prompts: the orchestrator prompt in orchestrator.py
    (fin_agent/agents/orchestrator.py) and the researcher prompt in
    researcher.py (fin_agent/agents/researcher.py).
  - Custom tools: tavily_search (with the budget guard), think_tool and
    save_final_report.
  - Guard middleware: research_guard.py (fin_agent/research_guard.py) enforces
    the 500-word note cap, the note path and the result cap.
    OrchestratorGuardMiddleware blocks the orchestrator's own file writes.
  - Glue: request.py (fin_agent/request.py) saves the original request, and
    main.py resets per-run state and starts the run.

  Not from Deep Agents: the word limits, Tavily budget, source-URL rules and the
  "Coverage and Gaps" check. We enforce those in code, because prompts alone
  aren't reliable.

> how the main agent delegates? explain it

● Delegation is Deep Agents' built-in task tool. We only supply the subagent
  definition and the instructions for using it.

  1. Registration. build_orchestrator in orchestrator.py
  (fin_agent/agents/orchestrator.py) passes
  subagents=[get_researcher_subagent(...)] to create_deep_agent. That spec has a
  name ("researcher"), a description, a system_prompt, its own tools
  (tavily_search, think_tool), a model, and its guard middleware. Deep Agents
  automatically gives the orchestrator a task tool. The tool's description lists
  the available subagents, using our description text.

  2. The decision is the model's. Our orchestrator prompt tells it to group the
  request into at most 3 focused tasks and to skip anything not asked for. It
  also says each brief must name all the companies, the topic and the period.
  Nothing in code decides the tasks. The model chooses, and the code only caps
  the number of tasks (via the Tavily guard).

  3. The call. The model emits something like:
  task(subagent_type="researcher",
       description="Compare MSFT and GOOGL on revenue growth and profitability,
  FY2025. Keep source URLs.")
  It can issue several task calls in one step, and they then run in parallel.
  The same researcher definition is reused each time. Only the brief changes.

  4. Isolation. The spec uses "mode": "isolated". The researcher starts with a
  fresh context containing only the brief. It doesn't see the user's request,
  the plan, or other tasks' results. It searches, reflects with think_tool, and
  writes a note to /notes/<slug>.md in the sandboxed filesystem.

  5. What comes back. Only the researcher's final message returns to the
  orchestrator, as the task tool result. ResearchGuardMiddleware.after_agent
  rewrites it so the first line is the real Notes file: <path>. It also
  truncates the message to 500 words. The raw search results and the note body
  stay out of the orchestrator's context.

  6. Later use. At synthesis the orchestrator calls read_file on the paths it
  collected. It then does the completeness check and calls save_final_report.

  The offline test tests/test_orchestrator.py exercises this path with scripted
  models.

> how the filesystem is used during synthesis?

● Setup. One FilesystemBackend (from get_backend() in researcher.py
  (fin_agent/agents/researcher.py)) is rooted at outputs/research/ with
  virtual_mode=True. It is shared by the orchestrator and the subagent. Paths
  look like /notes/x.md and can't escape that folder.

  Before synthesis. The researcher wrote its detailed findings to
  /notes/<slug>.md, capped at 500 words and with five required sections. The
  orchestrator's context holds only the short summary and the Notes file: path
  from each task, not the findings.

  During synthesis (step 6 of the orchestrator prompt):
  1. The orchestrator calls the built-in read_file on each /notes/... path it
     collected. It can use ls or glob on /notes if a path is missing.
  2. Only now do the note contents enter its context, one note at a time. With
     at most 3 notes of 500 words each, that is small.
  3. It writes the comparison from those notes only, keeping the source URLs
     from the "Financial Facts" and "Sources" sections. The "Caveats" sections
     feed the gap flags.
  4. If a task returned NOT SAVED, there is no note to read, so its findings are
     treated as unverified.

  Writing. The orchestrator cannot write to the filesystem, because
  OrchestratorGuardMiddleware blocks write_file, edit_file and delete. It saves
  the report through save_final_report, which writes outputs/final_report.md
  outside the sandbox.

  Why this design. The search noise stays inside the researcher's context, the
  evidence persists on disk, and the orchestrator reads only what it needs, when
  it needs it. main.py clears old notes at the start of each run, so synthesis
  can't pick up stale files.

> explain how is the final report generate and how the sub agent output is used
  to generate it? is the final report created only using the sub agent output
  or not

● How the report is generated

  The orchestrator model writes the report itself. No code generates it. The
  model composes the markdown in the arguments of one
  save_final_report(markdown=...) call. The tool only validates it (700 words or
  fewer, a "Coverage and Gaps" section, source URLs) and writes it to
  outputs/final_report.md. If validation fails, the tool returns an error and
  the model shortens the report and calls the tool again.

  How the subagent output is used

  There are two kinds of subagent output.
  1. The reply is a short summary plus the Notes file: path. It sits in the
     orchestrator's context from the start and tells it what was found and where
     the note is.
  2. The note is a markdown file on disk, with the facts, figures, URLs and
     caveats. The orchestrator reads it with read_file at synthesis and works
     from that.

  The prompt tells the orchestrator to synthesize from the notes and to keep
  every figure's source URL. It also tells the orchestrator to flag anything
  unverified, stale or not found.

  Is it built only from subagent output?

  The intended design is yes for facts. The orchestrator has no web-search tool,
  so it has no way to gather new facts. Its prompt forbids inventing numbers
  and says to build the comparison from the notes only.

  It is not enforced in code, though. The orchestrator model also contributes:
  - Structure and wording: the summary, the comparison framing and the
    conclusions are its own writing.
  - The user's request: it is in the conversation, so it decides which
    dimensions to cover.
  - Its own knowledge: it could add a figure from memory, and nothing checks
    that. Code only checks that the report has some URL, not that each number
    traces to a note.

  If you want that guarantee, a simple next step is a code check that every URL
  in the report appears in one of the notes.

  Design tradeoff
  - The model chooses the tasks, because that flexibility is the point of a
    planning agent. Code enforces the hard limits: the ceiling, scope and
    coverage.
  - Code can't judge whether a task question is a good one. Lazy but legal plans
    are possible, such as one vague task for everything.
  - Matching dimension names is plain text comparison, so a model that renames a
    dimension mid-plan can be rejected on a technicality. The error message
    tells it how to fix that, and it can resubmit.
  - Forcing a plan before delegation adds one tool call per run. In exchange you
    get a decomposition you can inspect and test.

> what happens when the user questions needs more than 3 agents to be
  initialised? how is the user query divided?

● Short version: nothing gets initialised beyond 3 tasks. There is one
  researcher definition, which runs once per task, so "more than 3 agents"
  really means "more than 3 research tasks". The ceiling is enforced in code,
  and the report discloses whatever couldn't be covered.

  How the query is divided
  1. The model extracts the companies and the dimensions the user asked for, in
     the user's own terms.
  2. It groups dimensions by the evidence they need. Revenue and profitability
     share earnings releases, so they merge into one task. Regulatory risks and
     outlook each need different sources, so they split.
  3. Each task is one specific question covering all the companies. Tasks split
     by dimension, not by company.

  When a request seems to need more than 3 tasks
  - The plan is rejected. submit_research_plan returns an error such as "4 tasks
    planned but only 3 remain (hard ceiling 3). Merge or drop tasks." The model
    then resubmits a smaller plan.
  - Merge, then skip. The model can merge more dimensions into broader tasks.
    For anything it can't fit, it must list the dimension under skipped with a
    reason. Code rejects a plan that leaves a requested dimension neither
    covered nor skipped.
  - Gaps are disclosed. The skipped dimensions appear in the report's "Coverage
    and Gaps" section.
  - Late gaps. If the completeness check finds a gap after delegation, the model
    may submit a follow-up plan, but only for the tasks left under the ceiling.
    The middleware refuses any task call past 3.

  Weaknesses
  - Many companies: a task covers all the companies, and each task has about 5
    searches with one company per query. With 4 or more companies, one task
    can't research each in depth, so the notes will be thin. The note's caveats
    and the coverage section should say so, but I haven't tested that case.
  - Many dimensions: broad merging reduces depth per dimension. That is the
    tradeoff of the 3-task and 15-search budget, which was your call for the
    POC.
  - No automatic batching: the system doesn't split a huge request into several
    runs. It tells the user what it left out. Raising the ceiling is a
    deliberate change in MAX_RESEARCH_TASKS and the Tavily limits, not something
    the agent does on its own.
