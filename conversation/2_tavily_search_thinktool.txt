  Files
  - fin_agent/tools/tavily_search.py holds the guard class and the tavily_search
    LangChain tool.
  - tests/test_tavily_search.py holds the tests.
  - .env.example lists the variable names. You should compare it with your real

  Your numbers don't match. The env example says 2 / 3 / 6, but your
  requirements say 3 per task and 9 per request. I made 3 / 3 / 9 the hard
  ceilings in code. The env vars can lower them but never raise them.
  .env.example has your 2 / 3 / 6, so those are the effective limits once the
  values are in .env. If you want 3 and 9 to apply, change the two values in
  .env. The "Request Tavily budget" log line prints whichever budget is actually
  in effect, so it will say 6 with your env values.

  Where the quota is enforced. It's in TavilyGuard.search(), the only code path
  that reaches Tavily, so a prompt can't bypass it. Each time the guard checks,
  in this order:
  1. A cached duplicate query returns the saved result and uses no budget.
  2. If the request budget is used up, the call is blocked.
  3. If it would start a new task beyond the task limit, it's blocked.
  4. If this task has used all its searches, it's blocked.
  5. From a task's second search onward, gap_reason is required.

  Only then does it reserve a slot and call Tavily.

  Per-task vs per-request limits.
  - Per task: a task is identified by the task_id the agent passes in (e.g.
    msft-revenue). Each task gets its own search count, and the number of
    distinct task ids is capped.
  - Per request: one running total across all tasks, reset by start_request().
    Your entry point should call it once per user request.
  - Second search: the guard can't judge whether a gap is real, so it requires a
    gap_reason of at least 15 characters, logs it, and rejects empty or trivial
    ones. That is a soft gate.

  When the budget is exhausted. The tool returns a string instead of raising an
  error and makes no Tavily call. It starts with
  [TAVILY_BLOCKED:REQUEST_BUDGET_EXHAUSTED], says not to retry, and tells the
  agent to continue with the evidence it has and flag gaps as unverified. The
  task-limit and gap-reason blocks work the same way. A call that fails at
  Tavily still counts, since it may have been billed.

  Source quality and safety.
  - Results are sorted and labelled primary (.gov sites and investor-relations
    pages), reputable (Reuters, Bloomberg, FT, WSJ and similar) or other.
  - Reddit, Quora, social media and YouTube are excluded.
  - Snippets are cut to 600 characters, so there are no page dumps.
  - Searches use basic depth and 4 results.
  - The key is read only from the environment and is redacted from any error
    text and logs.

  Logging example: Request Tavily budget: 9 (...), then Research task 1
  (msft-revenue), then Tavily call 1/9 (task 1: 1/3) | query=....

  Testing the quota without 9 real calls
  - pytest tests/test_tavily_search.py -v runs everything offline. Build

  - For a quick real-world check, set TAVILY_MAX_CALLS_PER_REQUEST=2 and call
    tavily_search three times. The third call comes back blocked after only two
    real calls.

● I added the reflection tool in fin_agent/tools/think_tool.py. The 4 new tests
  pass along with the earlier ones (19 total). It's a plain function and doesn't
  call any model or Tavily.

  What it does. The model calls think_tool with these fields:
  - evidence_summary
  - evidence_sufficient
  - important_gap
  - sources_conflict
  - second_search_justified
  - include_in_notes

  The tool runs a few fixed checks and returns a short decision:
  - Search without a gap: if the model asks for another search but names no gap
    or conflict, the tool overrides it with STOP_SEARCHING.
  - Justified search: otherwise you get SEARCH_AGAIN plus a ready-made
    gap_reason to pass to tavily_search. That ties it to the second-search gate
    from earlier.
  - Conflicts: a conflict is flagged so both figures are reported with their
    sources and marked unverified.
  - Stated gap: a gap raised despite sufficient evidence is recorded as a caveat
    in the notes.
  - Include in notes: whatever the model puts there is echoed back so it ends up
    in the notes file.
  - Logging: each reflection is logged at INFO.

  Why a tool and not another agent
  - No new reasoning needed: the model needs a place to write down its reasoning
    and commit to a decision, not a second model's opinion. A tool gives that
    structure.
  - Cost and speed: an agent would add another LLM call every time, which means
    more cost and latency. The tool is free and instant.
  - Context: a separate agent would need the evidence passed to it, and it would
    only repeat what the researcher already knows. The tool runs in the
    researcher's own context.
  - Enforcement: it applies the same rules every time, so it can't be talked
    into a weak decision. An LLM verifier can, and it can also be wrong.
  - Your constraints: it fits "one orchestrator + one reusable researcher" and
    the "no hand-built workflow" rule.

  The limit of this design. The checks only look at what the model writes, so a
  model can still claim a gap that doesn't exist. The real protection is still
  the hard budget in the Tavily guard.
