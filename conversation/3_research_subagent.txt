  1. How the subagent works

  - The parent calls the task tool with subagent_type="researcher" and one
    self-contained brief.
  - The researcher runs in its own isolated context, so it sees only that brief.
  - It follows the prompt in fin_agent/agents/researcher.py:
    a. Pick a task_id slug.
    b. Run tavily_search.
    c. Run think_tool.
    d. Search again only if think_tool says SEARCH_AGAIN, up to 3 searches.
    e. Write the note.
    f. Reply with the note path and a few bullets.
  - The Tavily guard blocks any call beyond the limits (3 per task, 3 tasks, 9
    per request).
  - ResearchGuardMiddleware (fin_agent/research_guard.py) enforces the size
    limits in code, not just in the prompt.

  2. How filesystem writing is done

  - The agent uses the built-in Deep Agents write_file tool. No custom
    file-writing code exists.
  - The backend is FilesystemBackend(root_dir=outputs/research,
    virtual_mode=True), so the agent sees / as that folder and can't reach .env
    or the rest of the repo.
  - /notes/jpm-bac-revenue.md is saved as
    outputs/research/notes/jpm-bac-revenue.md on disk.
  - Before each write the middleware checks three things:
    - Path: it must match /notes/<slug>.md.
    - Size: the note must be 350 words or fewer.
    - Sections: it must have all five required sections.
  - If a check fails, the model gets an error message and nothing is saved, so
    it shortens the note and retries. edit_file and delete are disabled, so a
    note can only be replaced whole through that check.

  3. Why the filesystem is useful here

  - Detailed findings with source URLs stay on disk instead of filling the
    orchestrator's context.
  - The parent only receives about 250 words per task, so three tasks cost far
    less context than three full research dumps.
  - Notes persist and can be inspected, which helps debugging and checking
    sources.
  - The report writer can re-read exact figures and URLs later instead of
    relying on a lossy summary.

  4. How the parent will consume the artifacts

  - Each task result starts with Notes file: /notes/<slug>.md, followed by
    headline bullets. The orchestrator keeps those paths and bullets in its
    context.
  - At synthesis time it calls read_file on each path. The parent shares the
    same backend, so the paths resolve.
  - It then writes /report.md, which lands at outputs/research/report.md,
    keeping the source URLs and caveats from the notes.
  - This is the next step. It needs the orchestrator prompt to say "collect the
    paths, then read them", and I haven't built it yet.

  The context flow

  Main Deep Agent
    │  task(description = focused brief, subagent_type = "researcher")
    ▼
  Researcher (isolated)  ── sees ONLY: its system prompt + the brief
    │   tavily_search ─▶ results ─┐
    │   think_tool    ─▶ reflection ├─ all of this lives in the researcher's own
  context
    │   write_file ──▶ outputs/research/notes/<slug>.md (full detail, source
  URLs) ◀── on disk
    ▼
  final message: "Notes file: /notes/<slug>.md" + short summary (≤500 words)
    │
    ▼
  Main Deep Agent  ── receives: ONE tool result with that text
                      keeps: summary + path.  Reads the note with read_file only
  when it needs the detail.

  What goes down (parent → child)
  - Only the brief text. The child doesn't see the user's original request, the
    parent's plan, or earlier research results. If the parent wants the child to
    know something, the parent must write it into the brief.

  What goes up (child → parent)
  - Only the child's last message. The raw search results, the think_tool output
    and the note body all stay behind. In the test log, 8 messages and 871
    characters of tool output stayed in the child, and the parent received an
    8-word reply.
  - The reply's first line is Notes file: <path>, so the parent knows where the
    detail is. That line is checked against the file the child actually saved,
    not just what the model claimed, and NOT SAVED appears if nothing was
    written.

  Where the detail lives
  - On disk, in outputs/research/notes/. The parent only reads it when it needs
    exact figures or source URLs, which is at synthesis time. A parent that
    reads every note would pay the cost of the full note in its own context, but
    that is a deliberate choice then.

  What is Deep Agents' own behaviour and what is ours
  - Isolation (brief down, final message up) is the library's behaviour; we
    pinned it with "mode": "isolated" and tested it.
  - Ours are only the note file, the path line and the size limits, the last two
    enforced in the existing guard.

  One thing to watch: the brief size is chosen by the parent model, so a parent
  could paste a lot of text down. The brief N words log line makes that visible.
  The orchestrator prompt should tell the parent to keep briefs short and
  self-contained.
